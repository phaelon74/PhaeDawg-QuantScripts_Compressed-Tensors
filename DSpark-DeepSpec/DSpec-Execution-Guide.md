# DSpec Execution Guide

**Training a DSpark speculative-decoding draft model with DeepSpec — applied to `TheDrummer/Behemoth-R1-123B-v2`**

Sources reviewed:

- Paper: [DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)
- Repository: [deepseek-ai/DeepSpec](https://github.com/deepseek-ai/DeepSpec)
- Target model: [TheDrummer/Behemoth-R1-123B-v2](https://huggingface.co/TheDrummer/Behemoth-R1-123B-v2) (finetune of `mistralai/Mistral-Large-Instruct-2411`)

## 1. What DSpark / DeepSpec actually are

**DSpark** is a draft-model architecture for speculative decoding. A small "draft" model proposes a block of tokens in one forward pass; the big "target" model (here: Behemoth) verifies the whole block in one forward pass and accepts the longest correct prefix. Output quality is mathematically identical to running the target model alone — you only gain speed.

DSpark's three pieces:

1. **Parallel backbone** (a DFlash-style drafter, ~5 transformer layers) that reads hidden states injected from several layers of the target model and predicts all block positions at once.
2. **Sequential head** (a low-rank "Markov head", rank 256) that adds a cheap left-to-right transition bias so later draft tokens condition on earlier ones. This is what fixes the acceptance-rate decay that pure parallel drafters suffer.
3. **Confidence head** (a single linear + sigmoid) that predicts per-position acceptance probability, used at serving time to truncate low-value draft suffixes.

**DeepSpec** is the training/eval repository: a three-stage data pipeline, a trainer, and an offline evaluator that measures accepted length (τ) on nine benchmarks. It does **not** include a production inference engine — but a community vLLM DSpark integration exists and is running in the wild on DGX Spark clusters (see §10 for links and what adapting it to Behemoth entails).

Paper headline results: +26–31% accepted length vs Eagle3, +16–18% vs DFlash on Qwen3-4B/8B/14B; 60–85% per-user speedup in DeepSeek's production deployment.

## 2. Answers to the feasibility questions

### 2a. What is needed to complete this on a model?

Five things, in order:

1. **The target model itself**, runnable locally as a Hugging Face `transformers` causal LM (the pipeline runs its forward pass to harvest hidden states) *and* servable behind an OpenAI-compatible endpoint (to regenerate training answers).
2. **A prompt dataset** — the recipe uses [`mlabonne/open-perfectblend`](https://huggingface.co/datasets/mlabonne/open-perfectblend) (1.3M prompts; chat/math/code/instruction-following). Responses are thrown away and regenerated by the target model so the draft learns the target's actual distribution.
3. **A three-stage data pipeline** (all in `scripts/data/`):
   - Stage 1: download + split prompts (`download_and_split.py`).
   - Stage 2: regenerate every assistant answer with the target model (`generate_train_data.py` against SGLang/vLLM servers).
   - Stage 3: precompute the **target cache** (`prepare_target_cache.py`) — one forward pass of the target over every training sequence, saving bf16 hidden states from the configured `target_layer_ids` plus the final hidden state, per token. This is the big-storage step.
4. **Training** (`train.py` + a config under `config/dspark/`) — trains only the draft model (backbone + Markov head + confidence head). The target model's embedding and LM head are copied in frozen; the target itself is never trained and is not needed on GPU during training (it's read once on CPU).
5. **Evaluation** (`eval.py`) — runs real speculative decoding with target + draft together and reports accepted length per domain.

Software: Python with `torch==2.9.1`, `transformers==5.10.2`, `datasets`, `openai` (see `requirements.txt`), plus SGLang or vLLM for stage 2. Linux with NVIDIA GPUs is assumed throughout (the launchers spawn one worker per visible GPU; training uses FlexAttention + `torch.compile`).

### 2b. Can this be performed on any model?

**The method, yes; the repo as-is, no.**

- The DSpark *algorithm* is architecture-agnostic — the paper demonstrates it on Qwen3 and Gemma4 and deploys it on DeepSeek-V4 (an MoE). Any dense or MoE causal LM can in principle get a DSpark drafter.
- The *code* implements exactly two target families: **Qwen3** and **Gemma4** (`deepspec/modeling/dspark/{qwen3,gemma4}`, `Qwen3DSparkTrainer`/`Gemma4DSparkTrainer`, matching evaluators, and only `"qwen"`/`"gemma4"` chat templates in `deepspec/data/parser.py`).
- For any other family you must write a port (~a day of focused work for a Mistral-style dense model, since it can be adapted from the Qwen3 files): a draft `modeling.py`/`config.py`, a trainer subclass, an evaluator registration, a chat-template entry, and a choice of `mask_token_id` and `target_layer_ids`. Details in §5.

Practical constraints that make a model a *good* candidate: standard HF `AutoModelForCausalLM` interface with `model.layers` you can hook; a tokenizer with a spare/unused token to serve as the mask token; and enough compute to run the target over the whole training set. Very large targets are possible (DeepSeek did V4) but the cost scales with target size — see 2d.

### 2c. What about `TheDrummer/Behemoth-R1-123B-v2`?

**Yes, it is a viable target — with a porting step and real scale costs.** Relevant facts from its config:

| Property | Value | Implication |
|---|---|---|
| Architecture | `MistralForCausalLM` | Not supported by DeepSpec — needs the Mistral port (§5). Architecturally it is very close to Qwen3 (RoPE + GQA + SiLU MLP + RMSNorm, no sliding window), so the Qwen3 DSpark files adapt cleanly. The main deltas: Mistral has no QK-norm and different attention head config (96 Q heads / 8 KV heads, head_dim 128). |
| Size | 123B dense, 88 layers, hidden 12288 | ~245 GB of BF16 weights. Every pipeline stage that touches the target must shard it across GPUs. |
| Vocab | 32,768 | Small vocab — makes the Markov head and frozen LM head cheap. No dedicated mask token, so you must repurpose an unused control token (§5). |
| Chat format | Mistral v7 (non-Tekken), `[SYSTEM_PROMPT]`/`[INST]` | Needs a new chat-template entry in `parser.py`. The model card warns wrong template/whitespace degrades output — use the tokenizer's built-in `apply_chat_template`. |
| Reasoning | Optional `<think>` prefill; "works great even without reasoning" | Train the drafter in the mode you will serve. The DeepSpec README explicitly warns drafters trained on non-thinking data underperform on thinking-mode traffic. Simplest path: regenerate data in non-thinking mode and serve non-thinking. |
| Domain | RP/creative finetune | Open-PerfectBlend is chat/math/code. Acceptance rates track domain match, so consider blending in prompts representative of your real usage (long-form creative chat) when regenerating data. |

### 2d. Requirements for Behemoth — can 4× RTX 6000 Pro Blackwell do it, and how much storage?

**Short answer: yes on GPUs (with two small code changes), and storage is the real constraint — budget ~30 TB of fast NVMe for a practical run; the paper's full recipe would need ~180 TB.**

Four RTX 6000 Pro Blackwell cards = 4 × 96 GB = **384 GB VRAM**. Stage by stage:

| Stage | What runs on GPU | Fits on 4×96 GB? |
|---|---|---|
| 2. Answer regeneration | Behemoth served by vLLM/SGLang, tensor-parallel 4 | **Yes.** ~61 GB weights/GPU (BF16 TP=4), ~30 GB/GPU left for KV cache. FP8 weight quant doubles KV headroom and speeds things up (minor distribution shift — acceptable for this stage). |
| 3. Target cache | One full forward of Behemoth per training sequence | **Yes, with a code change.** The stock script loads the whole model onto *each* GPU (one worker per GPU) — 245 GB does not fit on 96 GB. Run a single worker with `device_map="auto"` pipeline sharding across all 4 cards instead (§6). |
| 4. Training | Draft model only (~7.7B trainable params: 5 Mistral-scale layers ≈ 6.9B + projection ≈ 0.75B + heads) | **Yes, with `full_shard`.** The `BF16Optimizer` keeps bf16 weights + bf16 grads + fp32 master + fp32 AdamW moments ≈ 16 bytes/param ≈ 123 GB of state — too much for one card (`no_shard` default), fine sharded 4 ways (~31 GB/GPU + activations). Set `train.sharding_strategy="full_shard"`. |
| 5. Evaluation | Behemoth + draft together | **Yes, with the same sharding change as stage 3** (the evaluator also loads the full target per GPU), or evaluate against an FP8 copy of the target. |

**Storage math.** The target cache stores, per token, bf16 hidden states for `len(target_layer_ids)` captured layers **plus** the final hidden state. With the default 5 captured layers:

- Behemoth: (5+1) × 12288 dims × 2 bytes = **147,456 bytes ≈ 144 KB per token**.
- Reference: Qwen3-4B is (5+1) × 2560 × 2 = 30 KB/token, and its documented full-recipe cache is **38 TB** → the recipe covers ≈ 1.24 billion cached tokens (1.3M samples × ~950 tokens avg at `max_length=4096`).
- Behemoth, full 1.3M-sample recipe: 1.24B tokens × 144 KB ≈ **~180 TB**. Not workstation-territory.

Practical sizing knobs (both officially suggested in `scripts/data/README.md`):

| Configuration | Cache size |
|---|---|
| Full recipe: 1.3M samples, 5 captured layers | ~180 TB |
| 200k samples, 5 layers | ~28 TB |
| 200k samples, 3 layers (`target_layer_ids` reduced; cache shrinks to (3+1)/(5+1)) | ~19 TB |
| 100k samples, 5 layers | ~14 TB |

On top of the cache: ~250 GB target weights (plus ~125 GB if you also keep an FP8 serving copy), a few GB of regenerated JSONL, ~15 GB per draft checkpoint (fp32 optimizer state included), eval datasets ~10 GB. **Recommendation: 200k samples, 5 layers, ≥ 30 TB free NVMe.**

**Time budget (rough, 200k samples ≈ 190M cached tokens):** regeneration is the long pole — generating ~190M tokens through a 123B model on 4 cards at a few thousand tok/s aggregate is on the order of **1–3 days**; cache prep is one prefill-style pass, **roughly a day**; training ~7.7B trainable params for 10 epochs (~1.9B tokens) is **several days to ~2 weeks** depending on achieved throughput. All stages are resumable/checkpointed.

## 5. Step 2 — Port DeepSpec to the Mistral family (one-time code work)

DeepSpec has no Mistral support; this is the prerequisite for everything after stage 2. Use the Qwen3 implementation as the template — Mistral-Large's architecture is a strict simplification of Qwen3's (no QK-norm, no sliding-window layer types).

1. **Draft model** — create `deepspec/modeling/dspark/mistral/` by copying `deepspec/modeling/dspark/qwen3/`:
   - `modeling.py`: rename `Qwen3DSparkModel` → `MistralDSparkModel`, set `architectures=["MistralDSparkModel"]`, remove Qwen3's `q_norm`/`k_norm` from the attention module, keep everything else (context-feature projection, mask-token block input, Markov head, confidence head, flex-attention mask) unchanged.
   - `config.py`: copy `build_draft_config` as-is; it only clones the target config and stamps draft fields, all of which exist on `MistralConfig`.
2. **Trainer** — in `deepspec/trainer/dspark_trainer.py`, add a `MistralDSparkTrainer(Qwen3DSparkTrainer)` that builds `MistralDSparkModel` (mirror the 5-line `Gemma4DSparkTrainer`). Export it from `deepspec/trainer/__init__.py`.
3. **Evaluator** — mirror `Gemma4DSparkEvaluator` in `deepspec/eval/dspark/evaluator.py` (`MistralDSparkEvaluator(Qwen3DSparkEvaluator)` with `draft_model_cls = MistralDSparkModel`) and register `"MistralDSparkModel"` in the `EVALUATORS` dict in `eval.py`.
4. **Chat template** — register a `"mistral_v7"` entry in `deepspec/data/parser.py`'s `TEMPLATE_REGISTRY` with the v7 (non-Tekken) markers, e.g. `assistant_header="[/INST]"`-style boundaries matched to what `tokenizer.apply_chat_template` actually emits. Verify by rendering one sample and checking the `loss_mask` covers exactly the assistant spans.
5. **Mask token** — Mistral's 32,768-token vocab has no `<mask>`. Pick an unused control/reserved token ID from the tokenizer (inspect `tokenizer.get_vocab()` for `[control_N]`-style tokens that never appear in data) and use it as `mask_token_id`. It only needs a stable embedding row; the draft model treats it as "empty slot to fill".
6. **Layer taps** — choose `target_layer_ids` spread evenly over Behemoth's 88 layers, excluding the final layer (the evaluator asserts this): `[2, 23, 44, 65, 86]` follows the same proportions as the shipped Qwen3 configs. Use 3 taps instead of 5 if you need to shrink the cache.

Sanity-check the port before burning storage: run stage 3 + training on a **tiny slice** (e.g. 500 samples) end-to-end first.

## 6. Step 3 — Regenerate answers with Behemoth

Serve Behemoth tensor-parallel across all 4 cards with any OpenAI-compatible engine, then run the regeneration client. With vLLM:

```bash
# Terminal 1 — server (TP=4; add --quantization fp8 for more KV headroom/throughput)
vllm serve TheDrummer/Behemoth-R1-123B-v2 \
    --tensor-parallel-size 4 \
    --max-model-len 8192 \
    --port 30000
```

```bash
# Terminal 2 — client
python scripts/data/generate_train_data.py \
    --model TheDrummer/Behemoth-R1-123B-v2 \
    --server-address 127.0.0.1:30000 \
    --concurrency 32 \
    --temperature 1.0 --top-p 1.0 --top-k -1 --min-p 0 \
    --max-tokens 4096 \
    --resume \
    --input-file-path train_datasets/perfectblend_train_200k.jsonl \
    --output-file-path train_datasets/behemoth_123b/perfectblend_train_regen.jsonl
```

Notes:

- Set sampling to how you intend to **serve** the model (the drafter learns this distribution). The Behemoth card gives no canonical sampler settings, so match your deployment settings.
- Non-thinking mode (no `<think>` prefill) is the simpler, recommended path per the DeepSpec README; a thinking-mode drafter needs thinking-mode training data.
- `--resume` makes this restartable; failures land in `*_error.jsonl`.
- Stop the server before stage 4 — the cache step needs all four GPUs.

## 7. Step 4 — Prepare the target cache (the storage-heavy step)

**Required modification:** `scripts/data/prepare_target_cache.py` spawns one worker per GPU and loads the *entire* target model on each — impossible for a 245 GB model on 96 GB cards. Change it to run a **single worker with the model pipeline-sharded across all 4 GPUs**:

```python
# in prepare_target_cache.py, replace the AutoModel loading with:
target_model = AutoModel.from_pretrained(
    config.model.target_model_name_or_path,
    dtype=torch.bfloat16,
    attn_implementation="sdpa",
    device_map="auto",          # shards the 88 layers across all visible GPUs
).eval()
# ...and launch with nprocs=1 (single worker), keeping batch inputs on cuda:0.
```

Then run:

```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
export MASTER_ADDR=127.0.0.1 MASTER_PORT=29500 RANK=0 WORLD_SIZE=1

python scripts/data/prepare_target_cache.py \
    --config config/dspark/dspark_behemoth_123b.py \
    --train-data-path train_datasets/behemoth_123b/perfectblend_train_regen.jsonl \
    --output-dir /mnt/bigdisk/deepspec/behemoth_123b_target_cache \
    --local-batch-size 4
```

- Point `--output-dir` at the big NVMe volume. Expect **~144 KB per token ⇒ ~28 TB for 200k samples** (5 taps + final hidden state, bf16).
- The writer shards output into 64 GB files and writes a manifest; the trainer validates the cache against the config, so the config used here must match the one used for training.

## 8. Step 5 — Configure and train the DSpark drafter

Create `config/dspark/dspark_behemoth_123b.py` by copying `config/dspark/dspark_qwen3_4b.py` and changing:

```python
from deepspec.trainer import MistralDSparkTrainer   # your port from §5

exp_name = "dspark_block7_behemoth_123b"

model = dict(
    target_model_name_or_path="TheDrummer/Behemoth-R1-123B-v2",  # or local path
    block_size=7,                     # paper default; 8–16 also viable (gains grow with block size)
    num_draft_layers=5,
    target_layer_ids=[2, 23, 44, 65, 86],   # must match the cache; never the final layer (87)
    mask_token_id=<your unused control token id>,   # from §5, step 5
    num_anchors=512,
    markov_rank=256,
    markov_head_type="vanilla",
    confidence_head_alpha=1.0,
    confidence_head_with_markov=True,
    loss_decay_gamma=4.0,
    ce_loss_alpha=0.1,
    l1_loss_alpha=0.9,
)

train = dict(
    trainer_cls=MistralDSparkTrainer,
    lr=6.0e-4,
    warmup_ratio=0.04,
    weight_decay=0.0,
    precision="bf16",
    local_batch_size=1,
    global_batch_size=512,
    num_train_epochs=10,
    max_train_steps=None,
    max_grad_norm=1.0,
    sharding_strategy="full_shard",   # REQUIRED on 96 GB cards (~123 GB optimizer state unsharded)
    torch_compile=True,               # set False if compile issues arise with the new model class
)

data = dict(
    target_cache_path=None,           # passed on the command line
    chat_template="mistral_v7",       # your registration from §5, step 4
    max_length=4096,
    num_workers=4,
)
```

Launch (single node, all 4 GPUs; `train.py` spawns one worker per visible GPU):

```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
export MASTER_ADDR=127.0.0.1 MASTER_PORT=29500 RANK=0 WORLD_SIZE=1

python train.py \
    --config config/dspark/dspark_behemoth_123b.py \
    --opts "data.target_cache_path=/mnt/bigdisk/deepspec/behemoth_123b_target_cache"
```

- During training only the ~7.7B-parameter draft model is on GPU; the 123B target is loaded once **on CPU** just to copy its frozen embedding + LM head (make sure you have ~250 GB of system RAM or swap for that moment, or load that copy with `dtype=torch.bfloat16` on a machine that has it).
- Checkpoints land in `~/checkpoints/deepspec/dspark_block7_behemoth_123b/step_*`; TensorBoard logs in `~/tensorboard/...`. Training auto-resumes from the latest checkpoint if interrupted.
- With 200k samples, `global_batch_size=512` and 10 epochs ⇒ ~3,900 optimizer steps/epoch, ~39k steps total.

## 9. Step 6 — Evaluate

`eval.py` has the same per-GPU full-model-load problem as the cache script (§7): apply the same `device_map="auto"` + single-worker change to the evaluator's `build_models` (in `deepspec/eval/dspark/evaluator.py`), or evaluate against an FP8 copy of Behemoth that fits differently. Then:

```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
python eval.py \
    --target_name_or_path TheDrummer/Behemoth-R1-123B-v2 \
    --draft_name_or_path ~/checkpoints/deepspec/dspark_block7_behemoth_123b/step_latest
```

This runs speculative decoding over gsm8k, math500, aime25, humaneval, mbpp, livecodebench, mt-bench, alpaca, and arena-hard-v2 and reports **accepted length τ per round** (higher = faster serving; the paper's Qwen3-scale drafters land at ~3.2–6.2 depending on domain). Use `--confidence-threshold 0.0` (default) to also collect confidence-head calibration stats. For an RP model, also eval on `eval_datasets/perfectblend.jsonl`-style held-out prompts — the standard benchmarks under-represent your domain.

## 10. After training: deployment reality check

DeepSpec ends at offline evaluation. To get real-world speedup from the trained drafter you need engine support — and a **community vLLM integration for DSpark now exists and is proven in the wild**:

- **DSpark serving is real today, via a community vLLM fork (not upstream vLLM).** DeepSeek released ready-made drafters (`DeepSeek-V4-Flash-DSpark`, `DeepSeek-V4-Pro-DSpark`) on Hugging Face, and the community runs them on 2× DGX Spark (GB10) at ~60–67 tok/s (vs ~40–45 plain decode) with up to 1M context. The stack: Rafael Caricio's DSpark vLLM integration + runtime overlay patches, launched with `--speculative-config '{"method":"dspark","num_speculative_tokens":5}'`. Reference recipes:
  - [tonyd2wild/DeepSeek-v4-Flash-DSpark-1M-NVFP4-KV-2x-DGX-Spark](https://github.com/tonyd2wild/DeepSeek-v4-Flash-DSpark-1M-NVFP4-KV-2x-DGX-Spark) (1M context, `nvfp4_ds_mla` KV, concurrency patch)
  - [tonyd2wild/DeepSeek-v4-Flash-DSpark-60-tok-s-900K-ctx-2x-DGX-Spark](https://github.com/tonyd2wild/DeepSeek-v4-Flash-DSpark-60-tok-s-900K-ctx-2x-DGX-Spark) (benchmarked ~58–67 tok/s, acceptance 0.62–0.73)
  - [MiaAI-Lab/DeepSeek-v4-Flash-DSpark-2x-DGX-Spark](https://github.com/MiaAI-Lab/DeepSeek-v4-Flash-DSpark-2x-DGX-Spark) (two-node packaging, env/NCCL details)
  - [NVIDIA developer forum thread](https://forums.developer.nvidia.com/t/deepseek-v4-flash-dspark-on-2x-dgx-spark-gb10-big-single-stream-speed-boost-60-67-tok-s-1m-context-now-with-concurrency/374846) (deployment discussion + measured numbers)
- **Caveats for a Behemoth drafter:** that integration is built around DeepSeek-V4's architecture (MLA/MoE target). A Mistral-family DSpark drafter would need porting inside that vLLM fork too — much less work than integrating from scratch, since the DSpark drafting/verification plumbing (`method: "dspark"`) already exists. Note also the in-the-wild recipes run with `VLLM_DSPARK_CONFIDENCE_SCHEDULER=off`, i.e. fixed-length verification without the paper's hardware-aware scheduler — that alone already delivers the measured speedups.
- Pragmatic options, in increasing effort: (a) research/benchmarking with `eval.py`'s built-in decoding loop; (b) adapt the community vLLM DSpark integration to the Mistral drafter with fixed-length verification; (c) full confidence-scheduler integration with an SPS(B) throughput profile of your engine, as described in paper §5.2.
- The confidence head requires **post-hoc STS calibration** on held-out data before its scores are used for scheduling (paper §3.2.1); with the scheduler off it is unused, so you can defer this.
- **Scope note:** the DGX Spark sightings are *inference* of DeepSeek's own released V4 drafters. Nobody has published DeepSpec *training* runs on DGX Sparks; the training pipeline in this guide still assumes your 4× RTX 6000 Pro workstation (or similar).

## 12. Storage deep-dive: why the cache is so big, and how to shrink it

### Why

The target cache stores, for **every token of every training sequence**, bf16 hidden states from the target model:

```text
bytes per token = (num_captured_layers + 1) × hidden_size × 2
                = (5 + 1) × 12288 × 2  =  147,456 B  ≈ 144 KB   (Behemoth defaults)
```

The `+1` is `target_last_hidden_states`, kept so training can reconstruct the target's output distribution through the frozen LM head (the TV / distribution-matching loss). Behemoth's hidden size (12,288) is 4.8× Qwen3-4B's (2,560), which is exactly why Qwen3-4B's documented 38 TB scales to ~180 TB here. The cache exists as a compute-for-storage trade: without it, all ~39k optimizer steps × 512-sample batches × 10 epochs would each require 123B-target forward passes.

Note what **cannot** be trimmed: prompt tokens. The draft model attends over target hidden states for the entire context, so caching only assistant-response tokens is not an option.

### Reduction levers

| Lever | Effort | Saving | Quality notes |
|---|---|---|---|
| Fewer samples (e.g. 200k → 50k) | Config only | Linear (4×) | Original Eagle drafters trained on ~68k conversations; 50–100k is a defensible floor. Below that the drafter underfits. |
| 3 captured layers instead of 5 (e.g. `target_layer_ids=[2, 44, 86]`) | Config only | 33% | Matches Eagle3's low/mid/high tap convention — a proven design point. Officially suggested in `scripts/data/README.md`. |
| Lower `max_length` 4096 → 2048 | Config only | ~10–20% | Average sample is only ~950 tokens; this just trims the long tail. Hurts long-context draft quality. |
| FP8 (E4M3, per-token scale) cache storage | Modify `AsyncTargetCacheWriter` + `CacheDataset` reader | 2× | Hidden-state features tolerate FP8 well. Safest variant: FP8 for captured layers, keep `target_last_hidden_states` bf16 (it defines the "ground-truth" target distribution) → ~40% saving. |
| Lossless compression (zstd etc.) | Low | ~1.1–1.3× | Not worth it — bf16 hidden states are near-random bits. |
| No cache: recompute target forwards during training (SpecForge-style online mode) | Major rewrite | ~100% | Requires the 123B target resident during training. FP8 target (~123 GB) + sharded draft training state (~123 GB) is borderline on 384 GB, and every step pays a 123B forward × 10 epochs. Not recommended on this rig. |

### Bare-minimum sizing (Behemoth, ~950 tokens/sample average)

| Configuration | Bytes/token | 50k samples | 100k samples | 200k samples |
|---|---|---|---|---|
| Guide baseline: 5 layers, bf16 | 144 KB | 7 TB | 14 TB | 28 TB |
| 3 layers, bf16 — **config-only minimum** | 96 KB | **4.7 TB** | 9.3 TB | 18.7 TB |
| 3 layers FP8 + last-hidden bf16 | 60 KB | 2.9 TB | 5.7 TB | 11.4 TB |
| Everything FP8 (incl. last hidden) — **practical minimum** | 48 KB | **2.3 TB** | 4.7 TB | 9.3 TB |
| Aggressive floor: 2 layers, all FP8 | 36 KB | 1.75 TB | 3.5 TB | 7 TB |

Bottom line: **~5 TB with zero code changes** (50k samples + 3 taps), **~2–3 TB with an FP8 cache writer**, ~1.75 TB at the aggressive floor. At these sizes the training-time read bandwidth also drops well below 1 GB/s, so a SATA SSD or fast RAID array becomes acceptable in place of NVMe. Start at the config-only minimum, validate end-to-end on a 500-sample slice, and only invest in the FP8 writer if the 4.7 TB footprint is still too large.
